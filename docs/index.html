01 마일스톤

문서 엔진 → 서비스 → 인증 → 화면 → LLM 순서로 쌓습니다. 각 단계는 실제 서식으로 잰 증거가 나와야 끝난 것으로 칩니다. 규모는 S·M·L 로 적었습니다.

  1. M0기반S완료

    테스트·린트가 한 명령으로 돈다. 경로·환경 설정과 로깅을 한 곳에 모았다.

  2. M1HWPX 코어 — 읽기·쓰기L완료

    서식 193개 전부 쓰기 → 저장 → 다시 읽기 일치: 표 칸 57,431, 행 복제 2,049, 누름틀 2,301. 병합 칸, 반복영역 행 늘리기, 수식 재계산(305개 해석)까지.

  3. M2서식 파이프라인 — 변환·스키마 추출M완료

    변환 193 · 추출 183, 실패 0, 채울 지점이 없는 서식 0. 스키마가 가리키는 칸 전부에 실제로 쓸 수 있음을 확인했다.

  4. M3검증 엔진L완료

    규칙 4종이 서식 183 / 107 / 49개에 적용된다. 올바른 값을 넣으면 오탐 0, 일부러 넣은 오류는 그 자리에서 그 코드로 잡힌다.

  5. M4변환 어댑터 — HWP·PDFS완료

    채운 서식을 HWP·PDF 로 바꾸고 한글이 다시 연다. 자동화가 비정상 종료해 남은 한글이 있어도 다음 변환이 멈추지 않는다. 시간 초과·재시도 1회·260자 넘는 경로까지.

  6. M5수직 슬라이스 — 서식 3종 관통M완료

    기안문(변형 10종 중 하나 선택·여러 문단 본문)·정산서(표 중심)·교통비 지급 내역서(반복영역+합계)가 명령줄 하나로 입력 → 검증 → HWPX → HWP·PDF 까지 통과한다. 서식 183개의 변형 230건 전부를 만들어 오류 0, 일부러 넣은 오류는 만들기 전에 그 자리에서 잡힌다.

  7. M6서비스·저장 (FastAPI)L완료

    API 만으로 새 문서 → 임시저장 → 재조회 → 검증 → 만들기 → 내려받기. 서식은 버전으로 쌓아 작성 당시 버전으로 계속 만들고, 완료 문서는 복제해서 고친다. 입력값·검증 결과·적용 규칙을 이력에 남긴다.

  8. M7인증 (IAM)M완료

    발급한 계정으로만 로그인하고 첫 로그인에 비밀번호를 바꾼다. 3회 실패 잠금, 30분 세션과 연장, 중복 로그인 차단. 남의 문서와 관리자 경로는 막힌다. 루트 관리자는 서버 CLI 로만 만든다.

  9. M8사용자 화면L완료

    서식 찾기·미리보기(서식과 같은 모양, 병합 포함) → 입력(엑셀 붙여넣기·자동 저장·실시간 점검) → 검증 → 오류 칸으로 이동 → HWP·PDF 내려받기 → 내 문서함·이력. 서식 3종을 브라우저에서 처음부터 내려받기까지 끝까지 만들었다. 묶음 파일은 서식 번호마다 따로 목록에 올린다.

  10. M9관리자 페이지L미착수

    새 서식을 올려 승인하면 사용자 화면에 나타난다. 입력폼·규칙·계정 관리.

  11. M10LLM·입력 자동화 (EXAONE 3.5)L다음 · M9 보다 먼저

    프롬프트 하나로 서식 칸을 채우고(프롬프트에 없는 숫자는 경고), 학생이 낸 입금계좌 확인서 HWP 로 명단을 채운다. 명단·계좌·주민등록번호는 LLM 에 넘기지 않는다. 본문 초안과 체크리스트 기반 정성 판정.

  12. M11문서 간 검증·운영 현황M미착수

    계획서–정산서 금액 대조, 통계·로그인 이력·감사 로그.

  13. M12클라우드 이전M미착수

    변환을 별도 워커로 떼어 내고 로컬과 같은 시나리오가 클라우드에서 통과한다.

04 실제 서식이 잡아낸 결함

코드로 만든 테스트만으로는 안 보이던 문제들입니다. 183개 서식 전부를 대상으로 하는 로컬 회귀 테스트와 한글 렌더링 확인에서 나왔고, 모두 고친 뒤 같은 테스트로 막아 두었습니다.

  • M1 쓰기

    처음부터 비어 있는 누름틀(직인·접수일 등)은 글자 자리가 없어 250곳이 조용히 안 채워졌다.

  • M1 쓰기

    명단 행을 늘리면 마지막 행의 굵은 아래 테두리까지 복제돼 늘린 행 사이에 이중선이 생겼다. 가운데 행을 복제하도록 고쳤다.

  • M1 속도

    칸 하나 쓸 때마다 문서 전체를 훑어 193개 라운드트립이 464초 걸렸다 → 35초.

  • M2 추출

    예시 이름을 띄어 쓴 홍 길 동, 여러 줄에 병합된 예시 항목 때문에 예시·데이터 행을 헤더로 잡았다.

  • M2 추출

    순번·금액 같은 숫자를 항목명으로 쓴 칸이 287개 → 0. 합계 행 아래 빈 줄이 합계 칸으로 잡힌 것도 바로잡았다.

  • M3 검증

    합계를 셀 때 연번과 날짜(2026.10.12 → 2026원)까지 더하는 오탐. 옛 엔진에도 있던 결함이었다.

  • M4 변환

    경로가 260자를 넘으면 한글이 이유 없이 저장에 실패한다. 짧은 임시 폴더에서 변환한 뒤 옮긴다.

  • M5 수식

    SUM(ABOVE) 가 빈 칸에서 멈춰 명단을 일부만 채우면 합계가 0이 됐다. 한글은 빈 칸을 건너뛴다. 고치자 서식 수식이 표시값과 맞는 수가 220 → 304/305 — 그동안 "낡은 값"으로 보던 84건이 이 결함이었다.

  • M5 추출

    수식이 읽는 빈 입력칸(정산서의 집행 금액 등) 131개가 글 칸으로 잡혀, 글을 넣으면 합계를 계산하지 못했다. 금액 칸으로 바로잡았다.

  • M5 생성

    쓰지 않은 명단 행에 미리 적힌 5,000 이 남아 수식 합계가 쓰지 않은 행까지 더했다. 쓰지 않은 행은 비운다.

  • M8 목록

    서로 다른 서식 5개를 묶은 인건비 입금계좌 확인서 등(누름틀 없음)이 한 서식으로 잡혔다. 누름틀 반복 대신 서식 머리의 번호 표시로 나눈다. 지난 학년도 [혁신 서식 7-01호] 안에 잘못 적힌 7-02호 는 파일 이름 번호와 대조해 거른다.

자리표시자가 아닌 예시 값(장소: 강남 코엑스, 20OO.OO.OO)은 입력칸으로 잡히지 않습니다. 지금은 칸 좌표로 덮어쓸 수 있고, 관리자 입력폼 관리에서 항목으로 승인하게 할 계획입니다.

결과물을 HWP 로 꼭 줘야 하는지 먼저 정하면 선택지가 줄어듭니다. 서버에서 한글을 자동화로 돌리는 라이선스도 확인이 필요합니다.

결정된 것 결정

입력은 프롬프트 → LLM 이 칸을 채움 → 확인. 명단·계좌는 입금계좌 확인서 HWP 를 올리거나 직접 입력하고 LLM 에 넘기지 않으며, 종이 명단은 OCR 하지 않습니다. 금액 형식(AMOUNT_INVALID)·학번 중복(ROW_DUPLICATE)은 경고로 넣었습니다. 로그인은 IAM 방식으로 도입했습니다(M7).
